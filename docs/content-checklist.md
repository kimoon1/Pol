## ERP

### 2026-11-15 문답으로 확인해 소스에 반영한 범위

- 이전 대화를 유지할 때 과거 조회 결과를 참조하는 요청의 처리 기준을 기획자와 여러 차례 R&D를 진행해 정했습니다. 후속 답변에서 컨텍스트에 포함할 최근 대화 범위를 제한하고, 범위 밖 과거 조회를 참조하면 사용자에게 확인 질문을 하도록 구현한 것을 확인했습니다.
- 사용자가 제시한 사례는 특정 기간의 데이터 조회 → 다른 작업의 대화 → 최초 조회 결과를 정리해 알림으로 등록하거나 Slack에 추가해 달라는 후속 요청입니다. 공개 문구는 이 사례와 최근 대화 범위·재확인 동작을 중심으로 설명합니다.
- '오래된 데이터'는 이 문답에서 초기 조회를 참조하는 대화 컨텍스트 문제를 의미합니다. 원본 데이터의 갱신 여부, 전체 이력의 삭제·요약·보관 방식, 재확인 후 재조회 여부, 정확한 대화 개수나 토큰 크기는 아직 확인하지 않았습니다.
- 권한 검사와 데이터 조회 기능이 늘어나면서 LangChain 에이전트 구성의 응답 속도 개선이 어려웠습니다. 도구 선택과 기능 조정을 빠르게 하기 위해 LangGraph 슈퍼바이저와 기능별 노드로 전환했습니다.
- 추가 답변으로 기존에는 하나의 LLM이 전체 흐름을 판단했고, LangGraph 전환 후에는 가벼운 초기 분류로 단순 공개 정보 조회와 부서별 민감 정보 조회의 흐름을 나눈 것을 확인했습니다. 사용자는 전환 후 응답 속도가 충분히 개선됐다고 설명했습니다.
- '가벼운 분류'를 별도 경량 모델 사용, LLM 미사용 분기, 권한 검사 생략으로 해석하지 않습니다. 구체적인 분류 구현·모델 구성은 아직 확인하지 않았습니다.
- 인사·회계·일반 부서·개발·기획 등의 요구사항과 세분화된 권한 조건을 기획자와 소통하며 정리했습니다.
- 프론트엔드 요청에 포함된 `user_pk`로 사용자의 부서·직책을 조회하는 툴을 구현했고, 슈퍼바이저가 조회한 사용자 정보를 각 에이전트에 함께 전달하도록 구성했습니다.
- 후속 답변에서 조회 툴·API 코드가 권한을 검사하고 허용되지 않은 요청을 차단하는 것을 확인했습니다. 사용자 정보 전달과 코드의 접근 검사를 구분해 설명합니다. `user_pk`와 로그인 사용자 간 검증 방식, 세부 권한 규칙, 실제 거부 응답과 검증 결과는 아직 확인하지 않았습니다.
- 응답 속도 개선은 사용자 설명으로 확인했습니다. 측정값이나 검증 방식은 아직 확인하지 않았으므로 응답 시간 단축률·호출 횟수 감소·운영 성과를 추정하지 않습니다.
- 벡터 검색 미사용은 구현 범위 설명으로 유지하고, 기술 선택의 이유로 추정하지 않습니다.

- 구체적인 실패 문구·오류 분류, 재시도·추가 질문 동작은 아직 확인하지 않았습니다.

## React 초기 구축과 PHP 전환 · 회사별 범위

### 2026-11-16 문답으로 확인한 범위

- 스냅컴퍼니는 PHP 백엔드를 유지하면서 React 초기 코드 구조를 설계하고 신규 화면과 API 통신 로직을 구현한 사례입니다. 기존 PHP 화면을 옮긴 작업으로 설명하지 않으며, 이 프로젝트에서 Node.js 전환은 하지 않았습니다.
- PHP 중심 개발팀을 PHP 백엔드와 React 프론트엔드로 나누는 방향에 맞춰 코드의 책임을 분리하고 개발 속도를 개선하는 것이 전환의 목적이었습니다. 조직 개편을 본인이 주도했다거나 개발 속도 개선을 측정했다는 주장은 하지 않습니다.
- 봄바람에서는 PHP 코드 자체를 Node.js와 React로 전환했다고 확인했습니다. 기존 봄바람 사례(`legacy-bom`)는 해당 범위로 유지하고 스냅컴퍼니 사례와 구분합니다.
- 스냅컴퍼니 사례는 React 초기 구축으로, 봄바람 사례는 React·Node.js 전환으로 구분합니다. 기존 `legacy-snap` URL은 링크 호환성을 위해 유지합니다.
- 개인 담당으로 확인되지 않은 구체적인 기능 목록은 기재하지 않고, 확인된 React 화면·PHP API 통신 구현 범위로 소개합니다. 업무 기능의 세부 설명은 공개 범위가 확인된 내용만 추가합니다.

### 이어서 확인할 항목

- 신규 화면의 검증과 배포 방식. 확인되지 않은 기능 단위 마이그레이션·운영 유지 성과는 개인 기여로 기재하지 않습니다.
- 개발 과정에서 확인한 변화나 피드백. 근거 없는 개발 속도 단축률은 추가하지 않습니다.

## 업로드 서버

### 사용자 설명으로 확인해 반영한 범위

- PHP 7.3 레거시를 PHP 8.3·DDD 기반으로 전면 리팩토링했습니다.
- 컨버터 서버는 파일 수신·Private S3 저장·검사를 담당하고, 검사 통과 작업을 업로드 서버로 전달합니다.
- 업로드 서버는 영상 Vimeo 연동, 이미지 크기별 변환·썸네일 생성을 담당하고 완료 정보를 SQS에 등록합니다.
- DB 큐를 SQS로 전환했으며 SQS 연동 코드는 본인이 담당했습니다. API 서버가 크론으로 완료 메시지를 소비해 파일 정보를 DB에 반영합니다.
- 업로드 서버의 DB 직접 접근을 제거했고, 기존 업로드 토큰 체계는 제거했습니다. 토큰 제거 자체를 보안 성과로 표현하지 않습니다.
- 서버 사양은 참고용 정보이므로 사이트·경력 요약·공개 문서에 기재하지 않습니다. 운영 환경은 서버별 역할과 Private S3·SQS·Vimeo 연동으로 설명합니다. 물리 서버 수나 active-active 방식은 추정하지 않습니다.
- 인프라·보안팀과 협업한 애플리케이션 코드 개발 사례입니다. 서버·AWS 리소스·rsync 환경 구축을 본인 기여로 표현하지 않습니다.
- S3 파일 전달 구조 개선은 별도 프로젝트로 유지합니다.
- DDD 적용 설명에는 DTO 통신 규칙, Repository·Service 코드 분리, Service에서 외부 연동 호출이라는 실제 구성만 사용합니다. 제공되지 않은 폴더·클래스·도메인 모델은 추정하지 않습니다.
- 파일 확장자 거부 → 프론트 알림, 확장자 통과 후 용량·해시 등 파일 검사 거부 → 프론트 알림, 모든 검사 통과 → 큐 등록을 사용자 확인 사례로 반영했습니다. 이를 자동화 테스트나 별도 테스트 로그로 표현하지 않습니다.

### 추가 자료가 필요한 항목

- 검사 항목과 실패 처리, 서버 간 요청 인증·인가 방식, 임시 파일·S3 접근 정책.
- 메시지 구조, 실제 큐 구성, 처리 실패·재시도·중복 메시지 처리와 API 크론의 DB 반영 방식.

- 확장자 허용 목록, 용량 제한값, 해시 검사 목적·알고리즘 등 세부 검사 규칙은 아직 제공되지 않았습니다.
- 첨부 보안 검토 문서의 RCE·검사 우회 등은 가설입니다. 실제 발견·해결한 취약점으로 공개하지 않습니다.
